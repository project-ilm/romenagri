The danda

Author’s note on the danda

The danda (। U+0964 and ॥ U+0965) was given a Romenagri spelling because the system is used primarily inside programming-language source: identifiers, string literals and comments. The linguistic layer was not the driving concern. The treatment of the danda is therefore recorded as a task that remains. The intention is to retire the special mapping and to leave sentence punctuation to the host language. Until that change is made, the existing bytes and keys remain in the tables for compatibility.

This note was carried over from an earlier draft of this site. The author has not yet confirmed its wording.

  • The single danda (U+0964) has the ISCII byte EA. The decoder writes | for it, and the lexical layer of rmn2acii never hands | to the parser: it copies it as the ASCII byte 7C, which acii2uni reads as U+007C. In the repository's own corpus, चोला। comes back as चोला|. The danda is outside the round-trip contract.
  • The double danda (U+0965) was written as its low byte 65, the letter e, before patch 0001, so that चोला॥ came back as चोलाe. Patch 0001 gave it the byte 87 and the string _vd, and it round-trips.
  • Nothing in this package retires or changes either of them. What the note says is to be done is for the author to decide. The row of the single danda (EA, |) is in the original tables; the row of the double danda (87, _vd) was added by patch 0001.

The eight cases of the nukta layer

Each case is a place where the layer, or the standard that it follows, asked for a decision or left a limit. A row says “all three” when the three forms give the same line, and otherwise has a row of its own for the forms that differ. Every code point is written out. The ACII column is what uni2acii wrote, the Romenagri column what acii2rmn made of it, and the last column what acii2uni wrote after rmn2acii had turned the Romenagri back into bytes.

C1. One letter in two spellings, and the eight composition exclusions

ड़ can be typed as the single code point U+095C or as ड and a nukta (U+0921 U+093C). The same holds for क़ख़ग़ज़ढ़फ़य़. Both spellings give BF E9.

Decision. The output is not fixed to NFC, and Unicode is not confused with the emission layers: it keeps a layer of its own, the form. The decomposition is not left as an “or” either: it is done explicitly at Level 1, the layer at which the sounds of the consonants are mapped, before the vowel signs are attached at Level 2. So the rule writes the consonant and the nukta, always, and no form writes the eight as single code points.

C2. The letters that have a code point of their own, against their pairs

Unicode gave a code point of its own to some letters with a nukta and none to others, with no uniform rule: ऩऱऴ against न, र, ळ and a nukta. ACII has two spellings of the first two (C7 and C6 E9, D0 and CF E9).

Decision. Inside, the layer is uniform: for all eleven, a character and a nukta. Nothing more is decided for this case (none). What comes out is the business of the form.

C3. A nukta after a halant

NFC would move the nukta in front of the halant and compose it, and E8 E9 is also how ISCII writes a soft halant, which made acii2rmn crash on it before the layer.

Decision. None taken. The layer leaves the sequence alone in every form.

C4. A nukta that does not follow a consonant directly

After a vowel sign, after a space, at the start of a line there is nothing to rebuild, and NFC agrees: a vowel sign blocks the composition.

Decision. No fixed format is locked in. The choice of NFC or NFD for what comes out is a user option: a command-line flag, an environment variable, a build macro or a function call. The default stays aligned with what the converters did, and users and integrators have full control at every level.

C5. The letter é is written as the nukta

uni2acii writes U+00E9 as its low byte E9, and E9 is the nukta. After न, र or ळ the byte is read as a nukta, as it was before the layer.

Decision. Encodings are not mixed. Once Unicode, or any other input encoding, has been consumed, it does not survive in a mixed state: the é is a normal character that has no ACII byte, and is treated like every other. What is added is a warning layer that notes this known bug of such converters. It is off by default, and enabled only by a flag (-w) or by the call that integrates the converter.

C6. The cluster ड़्व with the single code point

Without the layer uni2acii wrote the low byte of U+095C, 5C, and acii2rmn lost it together with the halant behind it: with patch 0001 alone the chain gave 5C E8 D4, wa, and व alone came back (section 15.1 of the specification).

Decision. It is not a case of its own and gets no special rule, no fix that names a cluster. It is resolved by the rule of C1: the precomposed consonant is broken into its base sound and the nukta before the halant and the adjunct consonant are bound at Level 2, so the formation of clusters is general.

C7. ऴ has no byte of its own

Decision. Nothing is assigned or mapped into D3, and no slot is made for it. Every internal representation keeps the one rule, a character and a nukta: ळ and the nukta, D2 E9.

C8. Extended clusters: ऱ्ह, ल्ह and the like

Clusters of a consonant, a halant and ह for which the table has special keys.

Decision. They are managed strictly as code point to code point mappings. The layer makes no assumption about how a font shapes them and takes nothing from the behaviour of an external transliteration; it adds nothing of its own to them. The fifteen reserved keys of section 11.3 of the specification stay untouched.

The fifteen reserved keys

Fifteen keys that the parser can ask for have no row in acii.h. When the parser asks for a missing key, lookup() returns NULL and the next strcat crashes. They are two things of different kinds. Thirteen are the Latin letter v typed after a consonant stem: v is not a letter of Romenagri (व is w), and the one spelling in which the parser accepts it is that of ळ, lvra, so every other stem followed by v asks for a key that no script has. Two are conjuncts typed as aspirates: Devanagari has no letter for an aspirated l or an aspirated ऱ, and Hindi and Marathi write those sounds as ल्ह and ऱ्ह; Romenagri's own spelling is l_ha and _rr_ha, but lh is what a person at a keyboard types.

The author is working on these himself, and nothing in this package changes them. The table shows what the compiled rmn2acii did with each typed form when the site was built. The nukta layer does not touch them either: ऱ्ह and ल्ह have always passed through the chain from Unicode (case C8).

What is open

Decided on 8 November and closed: the form is a user option and the default is what the converters always wrote (C1, C4); the rule is uniform, a character and a nukta, and is applied before anything is bound (C1, C2, C6); ऴ takes no byte of its own and D3 is not assigned (C7); the clusters get no special cases (C6, C8); a mixed encoding is not repaired, only reported, on request (C5); no decision on a nukta after a halant (C3); the fifteen reserved keys are not touched (C8).

Left to the reader:

  1. The form for a pipeline. The default is asis. A pipeline that compares or stores text in NFC sets nfc on both converters (ROMENAGRI_NUKTA_FORM=nfc does it for a whole script); one that wants every nukta letter as a pair sets nfd.
  2. Reordering. Folding a nukta that follows a halant needs a decision between a nukta and ISCII's soft halant, which is written E8 E9 as well. The converters do not make it.
  3. A fourth form, all eleven letters as single code points, is a table row and a few lines away. Any normaliser would split the eight again.
  4. The converters as functions. The conversion loops are in the main of each program. nukta_set_form() and nukta_options() give a program that includes nukta.h the form and the options; calling the loops themselves as functions would mean moving them out of main, which the patch does not do.
  5. The low-byte fallback for everything else. A code point that has no row is written as its low byte, which ACII reads as another character (the table below). The cure is to deal with such characters before uni2acii; the warning layer shows which ones there are.
